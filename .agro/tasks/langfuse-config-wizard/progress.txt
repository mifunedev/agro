2026-09-21 execute/oracle-audit — advisor fault-injected the deny-rule-removal case that T3 could not
  (T3 was excluded from editing the settings file). Removed all 9 config-path deny rules: 76 -> 67.
  Result: 2 failed / 17 passed, NOT the 3 failures T3's reasoning predicted.
  The Bash deny assertion passed with every config-path guard gone. Cause: its probe command begins
  with the verb 'cat', and an unrelated dotenv-oriented deny rule keyed on that verb matches it,
  because the fragment filename ends in the dotenv suffix. The assertion's title claims path
  coverage; its evidence is a verb-specific rule that has nothing to do with the path guard.
  Why it matters: the verb-specific rule covers one command; the path guard covers every command
  naming the path. Deleting the path guard narrows real protection, and this test would stay green
  through that change. Textbook pattern-evals-unexercised-oracle.
  Routed back to T3 with the settings-file injection explicitly authorized.
  NOTE for the PR body: this is the SECOND oracle defect found by injection in this build. T2 found
  the first, where an ambient exported base-URL variable in this session masked the set -a
  requirement. Both were invisible to a green run. Together they are the evidence that the
  fault-injection requirement earned its cost, and both belong under 'What was built'.
