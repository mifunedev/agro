## User Stories

- As an **operator**, I want to approve or reject an escalation with a Slack reaction so that I decide from my phone.
- As an **operator**, I want only my Slack user to count as a decision so that no agent can approve its own escalation.
- As an **unattended session**, I want one tested command that reads the operator decision so that I act only after a human decides.
- As an **operator** of a Slack gateway, I want a documented app setup that works so that the bot gets commands and events.

---

## Summary

The `/escalate` skill delivers an escalation to Slack through `.agro/skills/escalate/scripts/escalate.sh`. The skill has no path that reads the operator's answer. Unattended loops that need an approval use GitHub comments instead. Every session on a host can share one `gh` login. A session on such a host can post the approving comment. Slack separates the identities: a bot posts as the bot user, and only the operator posts as the operator's member ID.

A field setup on 2026-09-26 found these gateway defects:

1. Two bridges that use one Slack app split events between hosts. A DM or an `/enable` goes to whichever connection Slack picks. The bridge on the other host saves the change in its own `~/.pi/msg-bridge.json`.
2. A new Slack app rejects `/enable` with "not a valid command". The bridge registers these slash commands: `/help`, `/trusted`, `/revoke`, `/channels`, `/enable`, `/disable`, and `/toggletools`. The app manifest must declare each command and the `commands` bot scope. The bridge accepts a DM command only when the text starts with `/`, so a leading space does not help.
3. `.agro/skills/escalate/scripts/escalate.sh` reads `PI_SLACK_BOT_TOKEN` only from the environment or `.devcontainer/.env`. The bridge stores the token at `~/.pi/msg-bridge.json` `.slack.botToken`, so a host install needs a manual export.
4. The repository secret guard correctly denies ad-hoc commands that put a token in an HTTP header. A decision reader must be a committed, tested script.

## Storage

N/A. The reader is stateless. The caller keeps its own state.

## Architectural Decisions

- The operator's Slack member ID is the only decision identity. Set the ID in `ESCALATE_OPERATOR_SLACK_ID`. Without that variable, use the first `slack:` entry of `.auth.trustedUsers`.
- The scripts never put the token on a command line, in output, or in a log.
- The reader answers one question for one message. Callers own their queues.

## Design Principles

- Keep one path to Slack for delivery and one for decisions.
- Make the human decision explicit and attributable.
- Report a missing Slack scope by name.

## Out of Scope

- Workflow-specific approval queues.
- Slack interactive buttons.
- Multi-operator approval.

## Acceptance Criteria

- [ ] `escalate-decision.sh --channel <id> --ts <ts>` prints `approve`, `reject`, or `none`, and exits 0.
- [ ] The reader counts ✅ (`white_check_mark`) and ❌ (`x`) reactions. The reader counts thread replies that start with `approve` or `reject`. Each counts only from the operator's member ID.
- [ ] A decision from another Slack user prints `none`.
- [ ] On a Slack API error, the reader exits 2 and prints the `error` and `needed` fields, for example `missing_scope` and `reactions:read`.
- [ ] `escalate.sh` and the reader take the bot token from `~/.pi/msg-bridge.json` `.slack.botToken` when `PI_SLACK_BOT_TOKEN` is unset, and never print the token.
- [ ] `escalate.sh --dry-run` output and its JSON result include the Slack `ts`.
- [ ] The Slack gateway documentation holds a complete app manifest. The manifest has the 7 bridge slash commands, the `commands` scope, `reactions:read`, the history scopes, and the message events. The documentation states that each host needs its own Slack app.
- [ ] Tests cover each reader case with a stub HTTP client and pass in CI.
