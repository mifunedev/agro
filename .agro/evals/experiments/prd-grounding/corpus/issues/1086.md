## Summary

Add `agro workspace` as the door for host workspace lifecycle, and stop
`agro harness install` and `agro tool install` from creating workspaces.

Accepts the direction sketched in #1070, narrowed to two subcommands.

## Problem

An operator creates a host AGRO workspace only as a side effect of an install.
`installOnHost` prompts `Workspace name [default]:` and clones `mifunedev/agro`
into `~/.agro/workspaces/<name>` (`.agro/cli/src/commands/harness.ts:396-424`).
`agro tool install` carries a second copy of that wizard
(`.agro/cli/src/commands/tool.ts:437-455`), which prompts for a free-form path
instead of a name. A tool install can therefore record a `harnessRoot` outside
`~/.agro/workspaces/`.

`agro harness install <id> --workspace beta` already clones a workspace without
a prompt. The capability exists. The missing piece is a door that creates a
workspace without also installing a harness.

## Scope

```
agro workspace create [<name>] [--path <dir>]   clone mifunedev/agro into a workspace
agro workspace list [--json]                    list workspaces and mark the default
```

`harness install --host` and `tool install --host` resolve a workspace and
refuse when none exists. Each refusal names `${bin} workspace create` and lists
every workspace that exists.

`create` never writes `harnessRoot`. The two install paths remain the only
writers of that key, which preserves their present behavior.

## Non-goals

- `agro workspace use` and `agro workspace status`.
- `agro workspace remove`.
- A `--default` flag on `create`.
- `--workspace <name>` on `tool install`.
- A new registry file. `list` scans `~/.agro/workspaces/` the way
  `registry.listEntries` scans `~/.agro/sandboxes/`.

## Notes

#1070 stays open as the RFC. This issue tracks the accepted, narrowed build.
