# PRD: Escalate Slack decisions

Status: DRAFT

## User Stories

### US-001: Resolve the bot token from the bridge config

**Description:** As a host operator, I want `escalate.sh` to read the bot token from the bridge config so that I do not export the token.

**Acceptance Criteria:**

- [ ] The new file `.agro/skills/escalate/scripts/slack-token.sh` defines one function that `escalate.sh` sources to resolve the token.
- [ ] The function resolves `PI_SLACK_BOT_TOKEN` in this order: the environment, `.devcontainer/.env`, then `.slack.botToken` in the file that `ESCALATE_BRIDGE_CONFIG` names (default `~/.pi/msg-bridge.json`).
- [ ] With `PI_SLACK_BOT_TOKEN` unset, no `.devcontainer/.env` token, and a bridge config that holds `.slack.botToken`, `escalate.sh --dry-run` prints `"tokenSource":"bridge-config"` in its JSON and exits 0.
- [ ] No stdout, stderr, or `escalations.jsonl` line from `escalate.sh` contains the token value.
- [ ] If no source holds a token, the Slack reason names all three sources.
- [ ] `shellcheck -S warning .agro/skills/escalate/scripts/*.sh` exits 0.

### US-002: Report the Slack message timestamp in every result

**Description:** As an unattended session, I want the Slack `ts` in every `escalate.sh` result so that I can pass the message to the decision reader.

**Acceptance Criteria:**

- [ ] The JSON that `escalate.sh --dry-run` prints has a `ts` key. The value is the empty string, because a dry run posts no message.
- [ ] After a delivered Slack post, the stdout JSON and the `escalations.jsonl` line carry the `ts` from the `chat.postMessage` response.
- [ ] `.agro/evals/probes/escalate-contract.sh` asserts the `ts` key in the dry-run JSON and exits 0.

### US-003: Add the decision reader

**Description:** As an unattended session, I want one tested command that reads the operator decision so that I act only after a human decides.

**Acceptance Criteria:**

- [ ] `.agro/skills/escalate/scripts/escalate-decision.sh --channel <id> --ts <ts>` prints exactly one of `approve`, `reject`, or `none` and exits 0.
- [ ] The reader resolves the operator ID from `ESCALATE_OPERATOR_SLACK_ID`. If that variable is unset, the reader uses the first `slack:` entry of `.auth.trustedUsers` in the bridge config, without the `slack:` prefix.
- [ ] If no operator ID resolves, the reader prints `escalate-decision: no operator Slack ID` to stderr and exits 2.
- [ ] The reader reads reactions with `reactions.get` and thread replies with `conversations.replies`.
- [ ] A `white_check_mark` reaction from the operator ID prints `approve`.
- [ ] An `x` reaction from the operator ID prints `reject`.
- [ ] A thread reply from the operator ID whose text starts with `approve` prints `approve`. A thread reply that starts with `reject` prints `reject`. The match ignores letter case and leading whitespace.
- [ ] If the operator gave both an approve signal and a reject signal, the reader prints `reject`.
- [ ] A reaction or a reply from any other user ID, the bot user included, prints `none`.
- [ ] If a Slack response has `"ok": false`, the reader prints the `error` and `needed` fields to stderr and exits 2. Example: `missing_scope needed=reactions:read`.
- [ ] If `curl` fails, the reader exits 2 and names the Slack method.
- [ ] Missing `--channel` or missing `--ts` exits 64.
- [ ] The reader sources `slack-token.sh` and never prints the token.
- [ ] `shellcheck -S warning .agro/skills/escalate/scripts/*.sh` exits 0.

### US-004: Prove the reader with a stub HTTP client

**Description:** As a maintainer, I want a probe that drives the reader against canned Slack responses so that CI proves each decision case.

**Acceptance Criteria:**

- [ ] The new probe `.agro/evals/probes/escalate-decision.sh` carries `# tier:`, `# source:`, and `# desc:` headers.
- [ ] The probe puts a stub `curl` first on `PATH`. The stub returns fixture JSON by Slack method and makes no network call.
- [ ] The probe covers these cases: approve by reaction, approve by thread reply, reject by reaction, reject by thread reply, both signals, a decision from another user, `ok: false` with `missing_scope`, no operator ID, and a token from the bridge config.
- [ ] The probe asserts that no output of the reader and of `escalate.sh --dry-run` contains the fixture token string.
- [ ] Each case asserts the stdout value and the exit code.
- [ ] Fault injection: a disposable copy of the reader that counts a decision from any user makes the probe exit 1 with a message that names the identity case.
- [ ] `bash .agro/skills/eval/run.sh` reports the probe as PASS.

### US-005: Document the decision path and the Slack app setup

**Description:** As an operator of a Slack gateway, I want a documented app setup that works so that the bot gets commands, events, and reactions.

**Acceptance Criteria:**

- [ ] `.agro/skills/escalate/SKILL.md` documents `escalate-decision.sh`: arguments, outputs, exit codes, the operator ID resolution, and the reject-wins rule.
- [ ] `.agro/skills/escalate/SKILL.md` Rule 5 and the "Receiving replies" entry no longer state that the skill receives no answer. The text states that a caller reads the decision once per run and keeps its own state.
- [ ] The token entry in the `## Resolution` section of `SKILL.md` names the bridge config as the third source.
- [ ] `docs/integrations/slack.md` states that each host needs its own Slack app, and states the reason: two bridges on one app split events between hosts.
- [ ] `docs/integrations/slack.md` states that the bridge accepts a DM command only when the text starts with `/`.
- [ ] `docs/integrations/slack.md` names `reactions:read` and the history scopes as the scopes the decision reader needs.
- [ ] `.agro/evals/probes/slack-admin-command-surface.sh` asserts the one-app-per-host statement and exits 0.
- [ ] `bash .agro/skills/ste/scripts/ste-check.sh .agro/skills/escalate/SKILL.md` reports no new finding.

## Summary

Verified current state:

- `.agro/skills/escalate/scripts/escalate.sh` posts one escalation. The script reads `PI_SLACK_BOT_TOKEN` from the environment, then from `.devcontainer/.env` (lines 79–83). The script does not read `~/.pi/msg-bridge.json` for the token.
- `escalate.sh` already returns `ts` in the delivered JSON and in the log line (lines 169, 196–209). The `--dry-run` JSON (lines 103–104) has no `ts` key.
- `escalate.sh` sends the token through a process-substitution header file, never on the command line. `escalate-contract.sh` guards that pattern.
- `.agro/skills/escalate/SKILL.md` Rule 5 states that the skill is one-way and receives no answer.
- `.pi/install/slack-manifest.yaml` and the YAML block in `docs/integrations/slack.md` are identical. Both already declare the 7 bridge slash commands and the `reactions:read`, `channels:history`, `groups:history`, and `im:history` scopes. Both already declare the `message.channels`, `message.groups`, and `message.im` events. `slack-admin-command-surface.sh` guards the manifest.
- The manifest does not declare the `commands` scope. The issue asks for the scope. This plan did not verify whether Slack adds the scope for a manifest that declares `slash_commands`. Open question 2 records this gap.
- No document states that each host needs its own Slack app.
- The bridge seed `.pi/msg-bridge.json` stores trust as `auth.trustedUsers` entries of the form `slack:U…`.
- The escalate probes run in CI through the `eval-probes` job of `.github/workflows/ci-harness.yml`. The `shellcheck` step already covers `.agro/skills/escalate/scripts/*.sh`.

Selected approach:

1. Extract the token resolution into `slack-token.sh`. Both scripts source that file, so one path resolves the token.
2. Add `ts` to the dry-run JSON.
3. Add `escalate-decision.sh`. The reader calls `reactions.get` and `conversations.replies` through the same header-file pattern. The reader filters every signal by the operator ID.
4. Prove the reader with a probe that puts a stub `curl` on `PATH`. The existing escalate tests are probes, so the new test follows the probe pattern and needs no new test runner.
5. Update `SKILL.md` and `docs/integrations/slack.md`.

N/A. The reader is stateless. The caller keeps its own state.

## Architectural Decisions

- The operator's Slack member ID is the only decision identity. `ESCALATE_OPERATOR_SLACK_ID` sets the ID. If the variable is unset, the first `slack:` entry of `.auth.trustedUsers` sets the ID.
- A reject signal from the operator wins over an approve signal. A conflict must not start an action that the operator also refused.
- The reader answers one question for one message. The reader does not poll, wait, or queue. Callers own their queues.
- The scripts never put the token on a command line, in output, or in a log.
- The reader reports a Slack API error with exit 2 and the `error` and `needed` fields, so a missing scope is named.
- The token order is environment, `.devcontainer/.env`, bridge config. The first two sources keep the order of `gateway.sh`.

## Design Principles

- Keep one path to Slack for delivery and one path for decisions.
- Keep one token resolver.
- Make the human decision explicit and attributable to one Slack member ID.
- Fail closed: a conflict gives `reject`, and an error gives exit 2, never `approve`.
- Report a missing Slack scope by name.
- Do not add explanatory comments to tracked code.

## Out of Scope

- Workflow-specific approval queues.
- Slack interactive buttons.
- Multi-operator approval.
- Polling or waiting inside the reader.
- Changes to `gateway.sh` token loading.
- A fix for the split of events between two bridges on one Slack app. The plan documents the one-app-per-host rule only.
- Public documentation in `mifunedev/agro-web`, unless open question 4 changes this.
