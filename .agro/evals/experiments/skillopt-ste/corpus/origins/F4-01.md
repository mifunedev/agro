## What & why

Replaces the hand-built in-tree Slack Pi extension (`.pi/extensions/slack/`, ~3,000 LOC) with the maintained community npm package **[`pi-messenger-bridge`](https://github.com/tintinweb/pi-messenger-bridge)** (MIT, multi-transport), pinned as `npm:pi-messenger-bridge@0.4.0`. Motivation: the custom bridge accreted recurring reliability issues (idle-death, Codex `previous_response_not_found`); adopting the popular package retires that maintenance burden.

Harness-infrastructure change only — no application/business logic.

## Key behavioral changes

| Axis | Before | After |
|---|---|---|
| Tokens | `SLACK_APP_TOKEN` / `SLACK_BOT_TOKEN` | `PI_SLACK_APP_TOKEN` / `PI_SLACK_BOT_TOKEN` |
| Config store | `.devcontainer/.env` | `.env` + `~/.pi/msg-bridge.json` (chmod 600) |
| Access control | static env allowlist (`SLACK_ALLOW_*`), deny-default | 6-digit challenge + `trustedUsers`, deny-default |
| Connect | on boot | `autoConnect:true` |

Both are **deny-by-default — no security regression.** The allowlist *mechanism* changes from static IDs to an interactive trust bootstrap; `oh config slack` can pre-seed the operator's Slack user ID into `auth.trustedUsers` to preserve the zero-touch headless UX.

## Operator migration

1. Re-run `oh config slack` (writes `PI_SLACK_*`, seeds `~/.pi/msg-bridge.json`, restarts `client-slack`).
2. Remove any old `SLACK_APP_TOKEN`/`SLACK_BOT_TOKEN` keys from `.devcontainer/.env` (the wizard prints this reminder).
3. First DM to the bot prints a 6-digit code in `tmux attach -t client-slack` — reply with it (or pre-seed your user ID in the wizard).
